CourseWave Backend — Current Context
====================================

Objective
---------
Consolidate the CourseWave backend into a single FastAPI service and finish the
requested refinements:
- JSON-only response caching.
- Configurable prefix-based rate limiting with a strategy-to-handler registry.
- Student auth methods (EMAIL | GOOGLE) with nullable password hashes.
- Removal of the transactional outbox model.
- A notification model and Celery task backed by RabbitMQ queues, Redis locks,
  retries, and a dead-letter queue.
- A typed Jinja email template manager for OTP and email verification messages,
  plus a notification provider registry with SendGrid email delivery.
- The backend is the public API; api_gateway/ has been deleted.
- RabbitMQ replaces Kafka.
- No Docker containers are started during development/validation.


Confirmed Requirements and Decisions
------------------------------------
Caching
- Cache only responses whose media type is exactly application/json.
- Media-type parameters are allowed, e.g. application/json; charset=utf-8.
- Do not cache application/problem+json or any other non-JSON media type.
- Only paths under CACHE_ROUTES are cache candidates. The tuple lives in
  backend/app/middleware/cache.py and contains /student/api/v1 and
  /instructor/api/v1. Matching is segment-aware, so /student/api/v10 does not
  match /student/api/v1.
- Paths outside CACHE_ROUTES bypass cache reads and writes and do not get an
  X-Cache header.
- Non-JSON GET responses under a cache route stream through without buffering
  and still get X-Cache: MISS.
- Public, cookie-free, non-authenticated 200 GET responses only.
- Cache key: cache:<path> plus ?<raw query string> when present.
- TTL: CACHE_TTL_SECONDS (420 seconds by default).
- Do not cache Set-Cookie, Cache-Control: no-store/private, Vary: *, streaming
  responses, or bodies over 1 MiB.
- Redis failures fail open.

Rate limiting
- Setting is ratelimit_routes: a native list[dict[str, Any]] whose entries are
  exactly {prefix, window_ms, strategy}.
- Defaults:
    {"prefix": "/student/api", "window_ms": 90000, "strategy": "fixed_window"}
    {"prefix": "*", "window_ms": 90000, "strategy": "fixed_window"}
- Unmatched paths use the fallback
  {"prefix": "*", "window_ms": 90000, "strategy": "fixed_window"}.
- Match request paths against configured prefixes in list order; the first
  matching prefix wins. `*` matches any path.
- Resolve strategy through backend/app/middleware/ratelimit/ratelimiter_registry.py.
- RATELIMITER_REGISTRY maps both fixed_window and token_bucket to async handlers.
- Handlers take the request and window_ms and return bool.
- The middleware pre-binds Redis and RATE_LIMIT_MAX with functools.partial.
- Handlers publish RateLimitResult via scope["state"]["ratelimit_result"].
- The middleware sets X-RateLimit-Limit, X-RateLimit-Remaining,
  X-RateLimit-Reset, and Retry-After (429 only) from that metadata.
- RATE_LIMIT_MAX remains the fixed-window request cap for both strategies.
- Route entries stay exactly three keys.
- Use ratelimit_ only for the new route setting; all other RATE_LIMIT_* names
  remain unchanged.
- RATE_LIMIT_WINDOW_MS was removed because each route carries window_ms.
- Unknown strategies log a warning and fall back to fixed_window.
- Redis failures fail open.

Notifications and Celery
- New service at backend/app/services/notification/ with exception/, model/,
  and task/process_notification.py.
- Notification (table "notification") fields:
    notification_id: UUID primary key (uuid4)
    type: NotificationType EMAIL = "email", PUSH = "push", SMS = "sms"
    payload: JSON object
    belongs_to: NotificationAudience STUDENT = "student",
                INSTRUCTOR = "instructor", ADMIN = "admin"
    user_id: UUID, indexed
    status: NotificationStatus PENDING = "pending",
            PROCESSED = "processed", FAILED = "failed"
    created_at / updated_at: timezone-aware datetimes
- Database enum names: notification_type, notification_audience, and
  notification_status. They store lowercase values.
- Notification.send() is a synchronous no-op placeholder. Real delivery code may
  raise NotificationError.
- Celery configuration lives in backend/celery_app.py. It imports
  app.services.notification.task.process_notification and exposes `app` for
  `celery -A celery_app`.
- Task name: notification.process_notification. Task options:
    max_retries=5
    default_retry_delay=10
    retry_backoff=10
    retry_jitter=True
    autoretry_for=(NotificationError,)
    acks_late=True
    reject_on_worker_lost=True
    acks_on_failure_or_timeout=False
- Global worker settings also set acks_late, reject_on_worker_lost,
  acks_on_failure_or_timeout=False, and worker_prefetch_multiplier=1.
- process_notification takes notification_id and runs its async database/Redis
  work with asyncio.run. The cached PostgreSQL engine is disposed and its cache
  cleared after each task.
- Task flow:
    1. Acquire Redis process lock notification:process:<id>, TTL 120 seconds.
    2. If busy, retry with countdown=120 seconds (the lock TTL).
    3. Load the notification.
    4. Return if status is already processed.
    5. Call notification.send().
    6. Success: set status=processed and commit.
    7. NotificationError before the last attempt: re-raise so Celery autoretries
       with exponential backoff and jitter.
    8. NotificationError on the last attempt: set status=failed, commit, then
       raise Reject(requeue=False) from the original error.
- There is no commit lock. The process lock is released in a finally block on
  success, retry, or reject.
- Queue topology:
    task: quorum queue, x-delivery-limit=5, dead-letter exchange task.dlx,
          dead-letter routing key task.dlq
    task.dlq: quorum queue, x-delivery-limit=-1
- Exchanges are topic exchanges so Celery uses RabbitMQ native delayed delivery
  for retry countdowns. Celery 5.5+ is required; the installed version is
  5.6.3.
- broker_native_delayed_delivery_queue_type is explicitly "quorum".
- The worker declares all configured queues on the worker_init signal because
  it consumes only `task` and would otherwise not declare task.dlq. The worker
  command is:
    celery -A celery_app worker --loglevel=INFO --queues=task
- A worker service using the backend image and shared environment anchor was
  added to docker-compose.yml. It waits for Redis, PostgreSQL, and RabbitMQ to
  become healthy.

Email Templates
- New service at
  backend/app/services/notification/template_manager/__init__.py.
- TemplateType is a str enum with OTP = "otp" and
  EMAIL_VERIFICATION = "email_verification".
- TemplateManager(type, content) normalizes either a string or TemplateType.
- get_template() uses template_registery to select a template directory and
  pinned template version, then returns a frozen `template` dataclass with
  body, version_number, and template_path fields. Registry entries no longer
  contain subjects; the version number is derived from filenames such as
  v1.html.
- template_build(template_path, content) is a static Jinja2 helper. Relative
  paths resolve from backend/.
- Registered templates:
    otp -> templates/email/otp/v1.html with content key `otp`
    email_verification -> templates/email/email_verification/v1.html with
                         content key `link`
- The template directory holds versioned files. The registry `template` value
  pins the active version; v2.html can be added and selected by changing the
  registry entry.
- Jinja2 was added to requirements.txt, and the Dockerfile copies templates/.

Notification Providers
- New package at backend/app/services/notification/provider/.
- ProviderType is a str enum with EMAIL = "email", PUSH = "push", and
  SMS = "sms".
- provider_registery.py creates `email_provider = EmailProvider()` and maps
  {"email": email_provider}; push and SMS are intentionally unregistered.
- ProviderManager.get_provider(provider_type) accepts a string or enum and
  raises ProviderNotFoundError for unknown or unregistered types.
- BaseProvider defines abstract process(notification).
- EmailProvider reads payload["template_type"], payload["content"], and the
  recipient from payload["to_email"] with payload["email"] as a fallback.
- EMAIL_SUBJECT_REGISTRY contains "email_verification" -> "verify your email"
  and "otp" -> "your verification code".
- EmailProvider renders with TemplateManager and sends a SendGrid Mail object.
  Logic errors raise ProviderError. SendGrid client and non-2xx response errors
  raise ProviderServiceNotAvailableError (alias ProviderServiceNotAvailbleError).
- ProviderNotFoundError and ProviderServiceNotAvailableError subclass
  NotificationError via ProviderError, so the existing Celery retry flow
  recognizes them.
- SendGrid settings use SENDGRID_API_KEY, SENDGRID_FROM_EMAIL, and
  SENDGRID_FROM_NAME, with placeholder defaults.
- NotificationCacheMixin uses synchronous Redis via
  create_sync_redis_client(settings).
- Processed-notification key format:
  notification:processed:<notification type>:<notification id>.
- The cached value is "processed" with a 240-second TTL. EmailProvider checks
  the key before processing and writes it only after a successful SendGrid send.
- Redis cache read/write failures fail open and log a warning.

Prior decisions that remain in place
- Student registration remains public and unchanged.
- Student.auth_method is an AuthMethod enum with EMAIL = "email" and
  GOOGLE = "google"; the database enum is named auth_method and stores the
  lowercase values.
- Student.password_hash is nullable with a NULL default, but email
  registration still hashes and stores a password.
- register_student sets auth_method=AuthMethod.EMAIL explicitly.
- The Outbox model and all outbox writes are removed.
- New error bodies use {"detail": "..."}.
- Compose service is named coursewave, builds ./backend, publishes 3000:8000.
- RabbitMQ replaces Kafka; Kafka and api_gateway/ are removed.
- Refresh is BaseHTTPMiddleware handling POST /auth/api/v1/token-refresh.
- Auth, Cache, RateLimit, RefreshToken, and RequestLogger are all Starlette
  BaseHTTPMiddleware; CORS remains the built-in CORSMiddleware.
- Cache only public GETs under CACHE_ROUTES (no Authorization, no Cookie, no
  authenticated session).
- Anonymous rate limiting keys on the socket IP.
- Middleware order is
  CORS -> RequestLogger -> Auth -> RateLimit -> RefreshToken -> Cache -> routes.
- Do not start Docker Desktop or any containers.
- utc_now lives in backend/app/base_utils and is re-exported by
  app.services.student.model.base for existing imports.

Known Gaps
- No notification enqueue endpoint or scheduler exists; another component must
  insert Notification rows and submit the task.
- Notification.send() remains a no-op and is not wired to ProviderManager, so
  successful tasks currently mark rows processed without external delivery.
- No login/token-issuer endpoint exists; auth validates existing access tokens
  and refresh rotates existing sessions only.
- No migration framework exists. Existing databases need the notification table
  created manually because create_all only creates missing tables on a fresh
  database. If the earlier schema exists, drop the unused release_after column
  manually.

Important Context
-----------------
- Authentication: HS256 Bearer access JWT signed with JWT_SECRET, type must be
  "access", sessionId must be present, and Redis key session:<sessionId> must
  hold {userId, role, email}. The parsed session is stored as
  request.state.user (scope["state"]["user"]).
- Refresh: signed cookie refresh=s:<JWT>.<HMAC-SHA256 base64 without padding>
  using COOKIE_SECRET. The refresh JWT uses JWT_SECRET, type must be "refresh",
  and the session TTL is extended to 604800 seconds. New access and refresh
  tokens reuse the same session ID.
- Cache routes: CACHE_ROUTES = ("/student/api/v1", "/instructor/api/v1") in
  cache.py. Matching is segment-aware; cache key is cache:<path>[?<query>].
- Rate-limit keys: ratelimit:<strategy>:<prefix>:<identifier>.
- Identifiers: authenticated session userId, otherwise socket IP.
- Student auth: AuthMethod.EMAIL.value == "email" and
  AuthMethod.GOOGLE.value == "google". password_hash is str | None.
- Notification enums store lowercase values; Notification.status defaults to
  pending.
- Notification process lock key: notification:process:<id>, with a 120-second
  TTL. A busy lock retries after the same 120-second TTL. There is no commit
  lock.
- TemplateManager accepts `otp` or `email_verification` as either a string or
  TemplateType. Email verification templates use the `link` content key; OTP
  templates use `otp`. Rendered templates expose body, version_number, and
  template_path; subjects are provider-owned.
- ProviderManager only has an `email` provider registered. Email notifications
  expect payload keys template_type, content, and to_email (email fallback).
- EmailProvider raises ProviderError for payload/rendering/message-building
  failures and ProviderServiceNotAvailableError for SendGrid client or non-2xx
  response failures.
- Processed notification cache key:
  notification:processed:<type>:<notification_id>; value "processed"; TTL 240
  seconds. Cache errors fail open.
- Retry countdowns use retry_backoff=10 with full jitter, so the nominal delays
  are 10, 20, 40, 80, and 160 seconds, capped at 600 seconds.
- Celery self.retry publishes a new message, so RabbitMQ x-delivery-limit=5
  covers broker redeliveries (worker crashes/requeues), not application
  retries. The final Reject(requeue=False) sends exhausted application failures
  to task.dlq immediately.
- The worker consumes only task; task.dlq is not consumed.
- Compose service publishes host port 3000 to container port 8000.
- Registration remains public at /student/api/v1/register.
- All new error responses use {"detail": "..."}.
- The repository root C:\Users\USER\CourseWave is the git repository; the
  remote is https://github.com/geraldrolland/coursewave.git (main).
- api_gateway/ was its own repository and has been removed permanently.
