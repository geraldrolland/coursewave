CourseWave Backend — Current Context
====================================

Objective
---------
Consolidate the CourseWave backend into a single FastAPI service and finish the
requested refinements:
- JSON-only response caching.
- Configurable prefix-based rate limiting with a strategy-to-handler registry.
- Student auth methods (EMAIL | GOOGLE) with nullable password hashes.
- Student login, email verification, password-reset email, and password-reset
  endpoints backed by Redis action tokens and the transactional outbox.
- Google OAuth login that exchanges the authorization code, creates or verifies
  the student, issues a session and refresh cookie, and redirects to the app.
- A protected current-session endpoint returning the authenticated user's id and
  email from Redis.
- A transactional outbox service dispatched by Celery Beat every 10 seconds.
- A notification model and Celery task backed by RabbitMQ queues, Redis locks,
  retries, and a dead-letter queue.
- A typed Jinja email template manager for OTP and email verification messages,
  plus a notification provider registry with SendGrid email, Kafka push, and
  Termii SMS delivery.
- Authenticated WebSocket notifications fed by a Kafka consumer.
- The backend is the public API; api_gateway/ has been deleted.
- RabbitMQ handles Celery tasks; Kafka handles push notification fan-out.
- No Docker containers are started during development/validation.


Confirmed Requirements and Decisions
------------------------------------
Caching
- Cache only responses whose media type is exactly application/json.
- Media-type parameters are allowed, e.g. application/json; charset=utf-8.
- Do not cache application/problem+json or any other non-JSON media type.
- Only paths under CACHE_ROUTES are cache candidates. The tuple lives in
  backend/app/middleware/cache.py and contains /student/api/v1 and
  /instructor/api/v1. Matching is segment-aware, so /student/api/v10 does not
  match /student/api/v1.
- Paths outside CACHE_ROUTES bypass cache reads and writes and do not get an
  X-Cache header.
- Non-JSON GET responses under a cache route stream through without buffering
  and still get X-Cache: MISS.
- Public, cookie-free, non-authenticated 200 GET responses only.
- Cache key: cache:<path> plus ?<raw query string> when present.
- TTL: CACHE_TTL_SECONDS (420 seconds by default).
- Only the response body is stored; response headers are never cached. Cache
  hits generate Content-Type: application/json, Content-Length, and X-Cache.
- Do not cache Set-Cookie, Cache-Control: no-store/private, or Vary: *.
- JSON bodies over 1 MiB are not cached. Chunked JSON responses under that
  limit are fully buffered and cached.
- Cacheable JSON responses are fully buffered before being returned, including
  oversized bodies.
- Redis failures fail open.

Rate limiting
- Setting is ratelimit_routes: a native list[dict[str, Any]] whose entries are
  exactly {prefix, window_ms, strategy}.
- Defaults:
    {"prefix": "/student/api", "window_ms": 90000, "strategy": "fixed_window"}
    {"prefix": "*", "window_ms": 90000, "strategy": "fixed_window"}
- Unmatched paths use the fallback
  {"prefix": "*", "window_ms": 90000, "strategy": "fixed_window"}.
- Match request paths against configured prefixes in list order; the first
  matching prefix wins. `*` matches any path.
- Resolve strategy through backend/app/middleware/ratelimit/ratelimiter_registry.py.
- RATELIMITER_REGISTRY maps both fixed_window and token_bucket to async handlers.
- Handlers take the request and window_ms and return bool.
- The middleware pre-binds Redis and RATE_LIMIT_MAX with functools.partial.
- Handlers publish RateLimitResult via scope["state"]["ratelimit_result"].
- The middleware sets X-RateLimit-Limit, X-RateLimit-Remaining,
  X-RateLimit-Reset, and Retry-After (429 only) from that metadata.
- RATE_LIMIT_MAX remains the fixed-window request cap for both strategies.
- Route entries stay exactly three keys.
- Use ratelimit_ only for the new route setting; all other RATE_LIMIT_* names
  remain unchanged.
- RATE_LIMIT_WINDOW_MS was removed because each route carries window_ms.
- Unknown strategies log a warning and fall back to fixed_window.
- Redis failures fail open.

Notifications and Celery
- New service at backend/app/services/notification/ with exception/, model/,
  and task/process_notification.py.
- Notification (table "notification") fields:
    notification_id: UUID primary key (uuid4)
    type: NotificationType EMAIL = "email", PUSH = "push", SMS = "sms"
    payload: JSON object
    belongs_to: NotificationAudience STUDENT = "student",
                INSTRUCTOR = "instructor", ADMIN = "admin"
    user_id: UUID, indexed
    status: NotificationStatus PENDING = "pending",
            PROCESSED = "processed", FAILED = "failed"
    created_at / updated_at: timezone-aware datetimes
- Database enum names: notification_type, notification_audience, and
  notification_status. They store lowercase values.
- Notification has no send() method. process_notification resolves a provider
  through ProviderManager and calls provider.process(notification).
- Celery configuration lives in backend/celery_app/__init__.py, with
  backend/celery_app/task_registry.py mapping short task names to callables. It
  imports app.services.notification.task.process_notification and
  app.services.outbox.task.process_outbox, and exposes `app` for
  `celery -A celery_app`.
- Task name: notification.process_notification. Task options:
    max_retries=5
    default_retry_delay=10
    acks_late=True
    reject_on_worker_lost=True
    acks_on_failure_or_timeout=False
- The task no longer sets autoretry_for, retry_backoff, or retry_jitter.
  max_retries/default_retry_delay are used only for Redis lock contention.
- Global worker settings also set acks_late, reject_on_worker_lost,
  acks_on_failure_or_timeout=False, and worker_prefetch_multiplier=1.
- process_notification takes notification_id and runs its async database/Redis
  work with asyncio.run. The cached PostgreSQL engine is disposed and its cache
  cleared after each task.
- Task flow:
    1. Acquire Redis process lock notification:process:<id>, TTL 120 seconds.
    2. If busy, retry with countdown=120 seconds (the lock TTL) and preserve
       custom headers such as x-retries while stripping RabbitMQ death headers
       and eta/expires.
    3. Load the notification.
    4. Return if status is not pending (processed and failed are both skipped).
    5. Resolve the provider from notification.type and call
       provider.process(notification).
    6. Success: set status=processed and commit.
    7. NotificationError: log, leave the status pending, and raise
       Reject(requeue=True) so RabbitMQ consumes the task delivery limit and
       then dead-letters the message to task.dlq.
- There is no commit lock. The process lock is released in a finally block on
  success, retry, or reject.
- Queue topology:
    task: quorum queue, x-delivery-limit=5, dead-letter exchange task.dlx,
          dead-letter routing key task.dlq
    task.dlq: quorum queue, x-delivery-limit=-1, consumed by dlq-consumer
    task.retry: quorum queue, no consumer, x-message-ttl=300000,
                dead-letter exchange task, dead-letter routing key task,
                x-dead-letter-strategy=at-least-once,
                x-overflow=reject-publish
- Exchanges are topic exchanges so Celery uses RabbitMQ native delayed delivery
  for retry countdowns. Celery 5.5+ is required; the installed version is
  5.7.0.
- broker_native_delayed_delivery_queue_type is explicitly "quorum".
- The worker declares all configured queues on the worker_init signal because
  it consumes only `task` and would otherwise not declare task.dlq or
  task.retry. The worker command is:
    celery -A celery_app worker --loglevel=INFO --queues=task
- A worker service using the backend image and shared environment anchor was
  added to docker-compose.yml. It waits for Redis, PostgreSQL, and RabbitMQ to
  become healthy.
- A dlq-consumer service runs `python -m dlq.consumer` from the same image and
  waits for PostgreSQL and RabbitMQ.

DLQ Consumer
- Package: backend/dlq with __init__.py, consumer.py, and handlers.py.
- TASK_RETRY = "task.retry", DLQ_MAX_RETRIES = 3, and
  TASK_RETRY_TTL_SECONDS = 300 live in celery_app/__init__.py.
- The consumer uses Kombu (already installed with Celery), not pika.
- It consumes task.dlq with prefetch_count=1 and publisher confirms enabled via
  transport_options={"confirm_publish": True}.
- DLQ retry budget:
    missing x-retries -> publish to task.retry with x-retries=1, then ack
    x-retries + 1 < 3 -> publish with x-retries + 1, then ack
    x-retries + 1 >= 3 -> run the terminal handler, then ack
  With DLQ_MAX_RETRIES=3 the terminal handler normally runs on the third DLQ
  arrival after two real five-minute retries.
- Republishing preserves the task body and custom headers, strips x-death and
  x-first-death-*/x-last-death-*, removes eta/expires, resets Celery's retries
  header to 0, sets x-retries, and publishes JSON with delivery_mode=2.
- Handler map:
    notification.process_notification -> mark_notif_failed
    process_notification -> mark_notif_failed
- Handler arguments are normalized with inspect.signature(handler).bind(*args,
  **kwargs) and invoked as handler(**bound.arguments). Async handlers are
  awaited.
- mark_notif_failed(notification_id) parses the UUID, uses a PostgreSQL row lock
  (with_for_update=True), leaves PROCESSED untouched, treats FAILED as
  idempotent, and changes PENDING to FAILED.
- Poison handling: unknown task names, malformed bodies, invalid x-retries,
  invalid notification IDs, and handler signature mismatches are logged and
  acked.
- Handler/database/publish failures are logged, throttled for 5 seconds, and
  rejected with requeue=True.
- The consumer acknowledges only after the retry publish is confirmed or the
  terminal handler succeeds. Duplicates remain acceptable under
  at-least-once delivery; the task and handler are idempotent.

Transactional Outbox
- New service at backend/app/services/outbox/ with model/outbox.py and
  task/process_outbox.py.
- Outbox (table "outbox") fields:
    id: UUID primary key (uuid4)
    status: OutboxStatus PENDING = "pending", PROCESSED = "processed",
            FAILED = "failed"
    retry_after: timezone-aware datetime or None, default None
    num_of_retries: int, default 0
    payload: JSON object
    table: string, e.g. "notification"
    ref_id: string containing the actual referenced row ID
- The database enum is named outbox_status and stores lowercase values.
- Outbox.payload shape:
    {"argument": {"notification_id": "<uuid>"},
     "task_name": "process_notification"}
- Celery Beat schedule runs outbox.process_outbox every 10 seconds. The task
  queries up to 50 rows with status=pending and retry_after null or in the past.
- Each row is processed in its own session/transaction:
    1. Acquire Redis lock outbox:process:<outbox id> with TTL 60 seconds.
    2. Re-load the row with FOR UPDATE SKIP LOCKED and re-check its state.
    3. Resolve task_name through TASK_REGISTRY.
    4. Invoke the callable with **payload["argument"].
       Synchronous Celery tasks run via asyncio.to_thread so their internal
       asyncio.run does not nest inside the outbox event loop.
    5. Success: status=processed, retry_after=None, commit.
- Lock contention logs and skips the row without consuming a retry.
- Failure: attempt = num_of_retries + 1.
    attempt < 5 -> num_of_retries=attempt and
      retry_after=utc_now() + 10 seconds * attempt; status stays pending.
    attempt >= 5 -> num_of_retries=5, retry_after=None, status=failed, and the
      row referenced by table/ref_id is marked failed (notification
      PROCESSED stays unchanged, FAILED is idempotent, PENDING becomes FAILED).
- The Redis lock is released in a finally block.
- TASK_REGISTRY = {"process_notification": process_notification,
  "process_outbox": process_outbox}. It lives in
  backend/celery_app/task_registry.py.
- Registration writes Student, Notification, and Outbox in one transaction and
  no longer publishes a task directly from the request.

Email Templates
- New service at
  backend/app/services/notification/template_manager/__init__.py.
- TemplateType is a str enum with OTP = "otp" and
  EMAIL_VERIFICATION = "email_verification".
- TemplateManager(type, content) normalizes either a string or TemplateType.
- get_template() uses template_registery to select a template directory and
  pinned template version, then returns a frozen `template` dataclass with
  body, version_number, and template_path fields. Registry entries no longer
  contain subjects; the version number is derived from filenames such as
  v1.html.
- template_build(template_path, content) is a static Jinja2 helper. Relative
  paths resolve from backend/.
- Registered templates:
    otp -> templates/email/otp/v1.html with content key `otp`
    email_verification -> templates/email/email_verification/v1.html with
                         content key `link`
- The template directory holds versioned files. The registry `template` value
  pins the active version; v2.html can be added and selected by changing the
  registry entry.
- Jinja2 was added to requirements.txt, and the Dockerfile copies templates/.

Notification Providers
- New package at backend/app/services/notification/provider/.
- ProviderType is a str enum with EMAIL = "email", PUSH = "push", and
  SMS = "sms".
- provider_registery.py creates email_provider = EmailProvider(),
  push_provider = PushProvider(), and sms_provider = SMSProvider(), then maps
  {"email": email_provider, "push": push_provider, "sms": sms_provider}.
- ProviderManager.get_provider(provider_type) accepts a string or enum and
  raises ProviderNotFoundError for unknown or unregistered types.
- BaseProvider defines abstract process(notification).
- EmailProvider reads payload["template_type"], payload["content"], and the
  recipient from payload["to_email"] with payload["email"] as a fallback.
- EMAIL_SUBJECT_REGISTRY contains "email_verification" -> "verify your email",
  "otp" -> "your verification code", and "forgot_password" ->
  "reset your password".
- EmailProvider renders with TemplateManager and sends a SendGrid Mail object.
  Logic errors raise ProviderError. SendGrid client and non-2xx response errors
  raise ProviderServiceNotAvailableError (alias ProviderServiceNotAvailbleError).
- ProviderNotFoundError and ProviderServiceNotAvailableError subclass
  NotificationError via ProviderError, so the existing Celery retry flow
  recognizes them.
- SendGrid settings use SENDGRID_API_KEY, SENDGRID_FROM_EMAIL, and
  SENDGRID_FROM_NAME, with placeholder defaults.
- PushProvider inherits NotificationCacheMixin and BaseProvider. It publishes
  notification.payload to the Kafka notification_topic through the singleton
  producer in
  backend/app/services/notification/pub_sub/kafka/kafka_producer.py.
- Kafka settings use notification_topic (default "notification") and
  kafka_bootstrap_servers (default "localhost:9092").
- The Kafka producer lazily creates a kafka-python KafkaProducer with a JSON
  value serializer, acks="all", and retries=3. send() waits for the future.
- SMSProvider inherits NotificationCacheMixin and BaseProvider and sends
  notification.payload through the Termii SDK (termii-client). It fills
  from/type/channel defaults from settings and caches successful sends.
- Termii settings use TERMII_API_KEY, TERMII_SENDER_ID, TERMII_CHANNEL, and
  TERMII_MESSAGE_TYPE, with placeholder defaults.
- NotificationCacheMixin uses synchronous Redis via
  create_sync_redis_client(settings).
- Processed-notification key format:
  notification:processed:<notification type>:<notification id>.
- The cached value is "processed" with a 240-second TTL. EmailProvider,
  PushProvider, and SMSProvider check the key before processing and write it
  only after a successful send.
- Redis cache read/write failures fail open and log a warning.

WebSocket Notifications
- New package at backend/app/services/notification/ws/.
- WebSocket route: /notification?token=<access-token>.
- authenticate_user decodes the access token, requires type=access, loads
  session:<sessionId> from Redis, and stores the session in
  websocket.state.user.
- Close codes: 1008 for missing/invalid tokens, wrong token type, invalid
  session ID, or missing session; 1011 for Redis or stored-session failures.
- WebsocketNotificationManager keeps connections as
  {user_id: list[WebSocket]}. register appends, remove deletes, and async send
  only targets WebSocketState.CONNECTED sockets.
- The endpoint registers the socket, sleeps in a loop, and removes the socket in
  finally. WEBSOCKET_SLEEP_SECONDS is 30.
- KafkaConsumer in pub_sub/kafka/kafka_consumer.py subscribes to
  notification_topic, parses messages, reads recipient_id and message, calls the
  WebSocket manager send, and commits offsets.
- Consumer settings: kafka_consumer_enabled (default false) and
  kafka_consumer_group_id (default coursewave-notification-websockets).
- The FastAPI lifespan starts/stops KafkaConsumer when enabled. Kafka polling
  and commits run on a dedicated single-thread executor.

Prior decisions that remain in place
- Student registration remains public and now uses the transactional outbox.
- Student.auth_method is an AuthMethod enum with EMAIL = "email" and
  GOOGLE = "google"; the database enum is named auth_method and stores the
  lowercase values.
- Student.password_hash is nullable with a NULL default, but email
  registration still hashes and stores a password.
- register_student sets auth_method=AuthMethod.EMAIL explicitly.
- The outbox was reintroduced under app/services/outbox; registration writes
  Student, Notification, and Outbox in one transaction.
- New error bodies use {"detail": "..."}.
- Compose service is named coursewave, builds ./backend, publishes 3000:8000.
- RabbitMQ handles Celery; Kafka is used only for push notifications;
  api_gateway/ is removed.
- Refresh is BaseHTTPMiddleware handling POST /auth/api/v1/token-refresh.
- Auth, Cache, RateLimit, RefreshToken, and RequestLogger are all Starlette
  BaseHTTPMiddleware; CORS remains the built-in CORSMiddleware.
- Cache only public GETs under CACHE_ROUTES (no Authorization, no Cookie, no
  authenticated session).
- Anonymous rate limiting keys on the socket IP.
- Middleware order is
  CORS -> RequestLogger -> Auth -> RateLimit -> RefreshToken -> Cache -> routes.
- Do not start Docker Desktop or any containers.
- utc_now lives in backend/app/base_utils and is re-exported by
  app.services.student.model.base for existing imports.

Known Gaps
- There is no general-purpose notification enqueue endpoint. New producers
  should insert an Outbox row in the same transaction as their business write.
- Kafka is not included in docker-compose.yml; push delivery and WebSocket
  fan-out require an external broker configured by
  kafka_bootstrap_servers.
- KAFKA_CONSUMER_ENABLED defaults to false; set it to true to start the
  Kafka-to-WebSocket consumer.
- SendGrid, Termii, Kafka, and Google OAuth defaults are placeholders that must
  be replaced.
- Google OAuth does not validate an OAuth state parameter; the callback only
  exchanges the code and redirects.
- Password reset does not invalidate existing access or refresh sessions.
- No migration framework exists. Existing databases need the notification and
  outbox tables created manually because create_all only creates missing tables
  on a fresh database. If the earlier schema exists, drop the unused
  release_after column manually.

Important Context
-----------------
- Authentication: HS256 Bearer access JWT signed with JWT_SECRET, type must be
  "access", sessionId must be present, and Redis key session:<sessionId> must
  hold {userId, role, email}. The parsed session is stored as
  request.state.user (scope["state"]["user"]).
- Refresh: signed cookie refresh=s:<JWT>.<HMAC-SHA256 base64 without padding>
  using COOKIE_SECRET. The refresh JWT uses JWT_SECRET, type must be "refresh",
  and the session TTL is extended to 604800 seconds. New access and refresh
  tokens reuse the same session ID.
- Cache routes: CACHE_ROUTES = ("/student/api/v1", "/instructor/api/v1") in
  cache.py. Matching is segment-aware; cache key is cache:<path>[?<query>].
- Rate-limit keys: ratelimit:<strategy>:<prefix>:<identifier>.
- Identifiers: authenticated session userId, otherwise socket IP.
- Student auth: AuthMethod.EMAIL.value == "email" and
  AuthMethod.GOOGLE.value == "google". password_hash is str | None.
- Student login: POST /student/api/v1/login. Unknown email, missing password
  hash, and wrong password all return 401 "Invalid email or password".
  Unverified accounts get a fresh 120-second verification token, notification,
  outbox row, and 403. Verified accounts get a UUID session ID stored at
  session:<id> as {userId, role: "student", email} with a 604800-second TTL,
  an access JWT in {"accessToken": ...}, and a signed refresh cookie.
- Google auth: GET /student/api/v1/google?code=... is public. It exchanges the
  code for an access token, fetches userinfo, looks up the student by normalized
  email, and either verifies the existing account or creates a new account with
  AuthMethod.GOOGLE, is_email_verified=true, and password_hash=None. Success
  reuses _create_login_tokens and build_refresh_cookie, then redirects 302 to
  {app_host}/dashboard. Missing code and any exception redirect 302 to
  {app_host}/login?msg=google_authentication_failed. Google credentials come
  from google_client_id, google_client_secret, and google_redirect_uri; all
  default to placeholders. OAuth state is not validated.
- Current session: GET /student/api/v1/me is protected; it is not in
  AUTH_EXCLUDE_PATHS. It reads request.state.user and returns {id, email}, where
  id is the session userId. It does not query the database or return role.
  Missing/invalid/expired tokens or sessions are rejected by AuthMiddleware.
  A session without non-empty string userId and email returns 401 "Invalid
  authentication session".
- Verify email: PATCH /student/api/v1/verify-email with {"token": ...}. The
  Redis token maps to a user UUID, the student is marked verified, and the token
  is deleted after commit. Missing/expired/malformed tokens return 400; a
  missing student returns 404. Already-verified accounts are idempotent.
- Password-reset email: POST /student/api/v1/email with {"email": ...}. Always
  returns the generic PASSWORD_RESET_SENT 200 response. Existing accounts get a
  120-second token whose link is {app_host}/forgot-password?token=..., plus a
  forgot_password notification and outbox row.
- Password reset: PATCH /student/api/v1/password-reset with password,
  confirm_password, and token. It reuses the registration password policy,
  hashes the new password, marks the email verified if needed, and deletes the
  token after commit. Invalid/expired tokens return 400; a missing student
  returns 404.
- Verification and password-reset tokens use the raw token as the Redis key and
  the user UUID as the value, matching registration; they are not
  purpose-namespaced.
- build_refresh_cookie in app/security.py creates the signed refresh Set-Cookie
  value for both login and RefreshTokenMiddleware.
- Notification enums store lowercase values; Notification.status defaults to
  pending.
- Notification process lock key: notification:process:<id>, with a 120-second
  TTL. A busy lock retries after the same 120-second TTL and preserves custom
  headers (notably x-retries). There is no commit lock.
- The task skips every status other than pending. Provider failures raise
  Reject(requeue=True) and leave the status pending; the DLQ consumer is the
  only component that marks a notification failed.
- TemplateManager accepts `otp`, `email_verification`, or `forgot_password` as
  either a string or TemplateType. Email verification and forgot-password
  templates use the `link` content key; OTP templates use `otp`. Rendered
  templates expose body, version_number, and template_path; subjects are
  provider-owned.
- Notification has no send() method. The task resolves ProviderManager using
  notification.type and calls provider.process(notification).
- ProviderManager has email, push, and sms providers registered. Email
  notifications expect payload keys template_type, content, and to_email
  (email fallback).
- EmailProvider raises ProviderError for payload/rendering/message-building
  failures and ProviderServiceNotAvailableError for SendGrid client or non-2xx
  response failures.
- PushProvider sends notification.payload to Kafka topic notification_topic
  through the KafkaProducer singleton. Kafka errors become
  ProviderServiceNotAvailableError.
- SMSProvider sends notification.payload through termii-client
  messaging.send, fills from/type/channel defaults from Termii settings, and
  uses NotificationCacheMixin before and after delivery.
- WebSocket route /notification requires ?token=<access token>.
  authenticate_user loads Redis session:<sessionId>, sets websocket.state.user,
  and closes with 1008 for auth/session errors or 1011 for Redis/session data
  failures.
- WebsocketNotificationManager keys connections by userId and sends only to
  CONNECTED sockets with multiple sockets per user.
- KafkaConsumer reads recipient_id/message from notification_topic payloads,
  sends through the WebSocket manager, and commits each offset.
- Processed notification cache key:
  notification:processed:<type>:<notification_id>; value "processed"; TTL 240
  seconds. Cache errors fail open.
- DLQ retry budget: missing x-retries republishes with 1; otherwise terminal
  only when x-retries + 1 >= 3. With DLQ_MAX_RETRIES=3 the handler normally runs
  on the third DLQ arrival after two real five-minute waits.
- Republishing to task.retry strips x-death and x-first-death-*/x-last-death-*,
  clears eta/expires, resets retries=0, preserves x-retries, and publishes JSON
  with delivery_mode=2. This avoids RabbitMQ cycle detection.
- Celery self.retry publishes a new message and resets RabbitMQ delivery counts.
  It is now used only for lock-contention retries; provider failures use
  Reject(requeue=True) and x-delivery-limit=5.
- The worker consumes only task. The dlq-consumer consumes only task.dlq, and
  task.retry has no consumer.
- The terminal handler mark_notif_failed uses a row lock, leaves processed
  notifications untouched, treats failed as idempotent, and changes pending to
  failed. Poison DLQ messages are acked; handler/DB/publish failures are
  throttled for 5 seconds and rejected with requeue=True.
- Outbox payload key is `argument` (singular) and holds the task kwargs.
  `table` plus `ref_id` identify the referenced row; ref_id stores the actual ID
  value, for example a notification UUID string.
- outbox.process_outbox runs every 10 seconds, selects at most 50 pending rows
  with retry_after null or in the past, and uses a 60-second Redis lock per row.
- Outbox retries use attempt = num_of_retries + 1. Below five, retry_after is
  utc_now() + 10 seconds * attempt. At five or more, the outbox row and its
  referenced notification become failed.
- The outbox invokes registry functions directly. Synchronous Celery tasks are
  run with asyncio.to_thread; this bypasses RabbitMQ retry/DLQ for
  outbox-dispatched notification tasks, whose retry budget is the outbox.
- Registration writes the verification Notification and Outbox row in the same
  transaction and does not publish the task from the request.
- Compose service publishes host port 3000 to container port 8000.
- Registration remains public at /student/api/v1/register.
- All new error responses use {"detail": "..."}.

  remote is https://github.com/geraldrolland/coursewave.git (main).
- api_gateway/ was its own repository and has been removed permanently.
